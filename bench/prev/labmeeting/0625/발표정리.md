# PART 1 — DPM API 설계

> **핵심 메시지:** 평범한 non-blocking epoll 서버/클라이언트를, BSD 콜을 `_dpm` 쌍둥이로 바꾸기만 하면 DPU data plane 위에서 돌린다. 그리고 이 추상화는 **공짜(zero-overhead)** — raw API와 동일한 240K 0-fail.

### 슬라이드 P1-1 · `fig01_socket_mapping.png` — 무엇을 만들었나
- DPUmesh raw C core(`dpumesh.h`)는 DOCA-flavored 저수준 콜(slot pool, req_id, pending table)이라 응용 개발자가 transport 내부를 알아야 했음.
- `dpm.h` façade: **BSD 콜 → `_dpm` twin** (`socket/accept/connect/read/write/sendfile/send/close`), **epoll은 그대로 native** — `event_fd_dpm(s)`를 listen socket처럼 등록.
- 동기 3가지: ① 기존 epoll 서버를 거의 손 안 대고 포팅 ② transport가 DPU/DPA에서 돌아 **host core를 응용에 돌려줌**(no in-host sidecar tax) ③ 친숙한 mental model.

### 슬라이드 P1-2 · `fig02_pair_not_connection.png` — ★ 가장 중요한 개념
- **`dpmconn_t`는 connection이 아니라 요청/응답 한 쌍(pair)이다.** handshake도, round-trip도, 지속 채널도 없음.
- `connect_dpm()`은 round-trip을 안 함 — 그냥 \"이 call의 target은 pod 11\"이라고 라벨만. 응답은 내부 **`req_id`로 correlate** (도착 순서 무관) → 여러 pair가 동시에 in-flight, **순서 뒤바뀌어 도착해도 OK**.
- socket(TCP stream)이 아니라 **RPC call**에 가깝다. single-shot — 한 번 쓰고 `close_dpm()`, 버림.
- 두 handle만 만짐: **`dpm_t`**(endpoint, 프로세스당 1개, 무거움) + **`dpmconn_t`**(요청당 1개, 쌈). `dpumesh_ctx_t` 엔진은 `dpm_t` 안에 숨김.

### 슬라이드 P1-3 · `fig03_facade_zero_overhead.png` — 추상화는 공짜다
- 전체 façade 스택(`bench_sock.c` 클라이언트 + `echo_sock.c` 서버, **raw API 콜 0개**)이 **raw API와 동일한 ~240K 0-fail** 천장.
- 클라이언트의 per-request malloc/free(single-shot conn)도 throughput을 제약하지 않음.
- **Implicit send(이번 주 핵심):** `write_dpm()`은 buffer만 → 다음 `read_dpm()`(클라) / `close_dpm()`(서버)이 자동 ship. 호출 패턴이 **socket과 글자 그대로 동일**(`accept→read→write→close`). `send_dpm()`은 confirm/retry용으로만 남김. 측정상 explicit-send와 latency **완전 동일** = send 제거 비용 0.

### 슬라이드 P1-4 · `fig04_facade_latency_idle.png` — latency + idle
- low–mid 부하 p50 **170–255µs** (single reactor, futex/thread contention 없음).
- **Idle CPU 1.2%** — native epoll에서 sleep → **notification-driven**(busy-poll 아님). ⇒ Part 2로 자연스럽게 연결.
- *정직하게:* 200K/240K의 p99(4.8/4.6ms)는 ~257K 천장 근처의 **saturation-edge 큐잉 noise**(같은 세션에서 run마다 0.4–2.5ms로 흔들림). deterministic 비용 아님.

**P1 발표자 talking points**
1. \"BSD 콜을 `_dpm`으로 바꾸면 평범한 epoll 앱이 DPU 위에서 돈다 — epoll은 안 건드린다.\"
2. \"`dpmconn_t`는 connection이 아니라 요청/응답 한 쌍\" — 이 한 가지가 socket과의 가장 큰 차이.
3. Implicit send로 호출 패턴이 socket과 구분 불가.
4. 추상화는 zero-overhead — 240K 0-fail, idle 1.2% notification-driven.

# PART 2 — Notification 기반으로의 변경

> **핵심 메시지:** busy-poll data plane을 event-driven으로 바꿔 idle CPU(ARM full core→2%)와 tail latency(200K p99 46→2.8ms)를 잡았다. 설계 원칙은 **\"POLL under load, SLEEP at idle\"** — 이건 leanness/tail lever이지 **throughput lever가 아니다**(천장은 불변).

### 슬라이드 P2-1 · `fig05_idle_cpu.png` — 동기 & 결과
- 세 개의 always-on busy-poller가 **idle에도 full core를 태움**: host `pe_progress`, DPU ARM `run_dpu_worker`(backoff 전혀 없어 ARM **100% even idle**), DPA EU.
- User directive: \"notification 올 때만 progress\". DOCA event path(`get_notification_handle → request_notification → epoll_wait → clear`)로 fd 위에서 sleep.
- 결과: **DPU ARM idle 100% → ~2%** (헤드라인), host RX thread 3%→0%.

### 슬라이드 P2-2 · `fig06_host_epoll_tail.png` — 사실 더 큰 승리는 tail latency
- HOST_EPOLL A/B: spin하던 `pe_progress`가 pinned core를 contend하며 tail을 부풀리고 있었음.
- **200K p99 46.5ms → 2.8ms (~16×)**, p999 57.7→4.7ms. (30K/100K는 거의 불변.)
- 세 레이어 공통 idiom = **drain → arm → re-poll → block**. host PE는 진짜 completion만 봐서(silent-wake 없음) 안전.

### 슬라이드 P2-3 · `fig07_grace_p50.png` — DPA EU grace-period polling
- DPA EU는 전용 FlexIO 실리콘 = ARM/host CPU 0원 → **가능한 한 연속으로 폴링**해야 latency에 유리.
- 예전: empty drain마다 park → moderate load의 gap에서 park → hop당 ~1ms WAKE 대기 → p50 ~2ms.
- 변경: **262144번 연속 빈 drain 후에만 park**. real inter-request gap은 grace window보다 훨씬 짧아 load 중엔 절대 park 안 함. → **p50 ~2ms → ~0.3ms (10×)**.

### 슬라이드 P2-4 · `fig08_poll_under_load.png` — ★ 과학적 결론 + the hard bug
- **EVENT_BLOCK 실험:** ARM을 host처럼 매 iteration epoll 통과시키면 → **천장 257K → 56K (4.5× 붕괴)**, 30K p50 233→676µs.
- 이유: completion당 ~5 syscalls(epoll_wait + notification×2 + clear×2)가 completion 간격 ~1µs를 못 따라감. **dedicated core는 load 중 spin이 free** → 재우면 throughput을 잃는다.
- ⇒ **\"POLL under load, SLEEP at idle\"** (drain-then-arm hybrid).
- **(말로 설명할 엔지니어링 스토리) THE KILLER BUG:** `EVENT_LOOP=1`에서 **multi-minute idle 후** 첫 테스트가 `0 RPS / redeploy 필요`. 원인 = DPA EU park/wake **lost-wakeup race**: park 직전 re-scan의 `handle_msgs()`가 arm 직후 도착한 1ms WAKE를 *소비*하면서 EU는 disarmed로 park → WAKE가 1024 recv credit까지 쌓여 영구 wedge. \"LONG idle 후에만\" 터진 이유 = park당 race 확률 극소, 누적으로 1 수렴. **FIX 2 = \"count, don't silently consume\"**: `handle_msgs()`가 개수 반환, **rings AND consumer-queue 둘 다 empty일 때만** park. 검증: amplified(IDLE_SPINS=256, ~1M parks/300s) + production(10-min idle + 원래 실패 명령) 둘 다 0-fail.

**P2 발표자 talking points**
1. 세 레이어(host PE / DPU ARM / DPA EU) 모두 event-driven, 공통 idiom = drain→arm→re-poll→block.
2. 이건 leanness/tail lever지 throughput lever가 아님 — 천장(257K)은 불변.
3. EVENT_PROBE로 \"consumer_pe가 usable notification을 raise하는가\"를 측정으로 확인(`timeout_WORK=0` = silent-miss 없음) 후 진행 — 추측 아님.
4. 가장 큰 교훈: **load 중 spin은 낭비가 아니라 필수**(EVENT_BLOCK 4.5× 붕괴). dedicated core라 free.
5. lost-wakeup race + FIX 2 = 이번 주 진짜 엔지니어링 스토리.

# PART 3 — 현재 구현에 대한 단계적 설명 (교수님 요청)

> **핵심 메시지:** 요청 하나는 **host → DPU → echo-host → DPU → host**의 **4-DMA-leg 체인**. DPU ARM은 body를 절대 안 읽고 `dst_pod_id`로만 **O(1) 라우팅**하는 *pod-id 라우터*. latency floor ≈ **220µs**(payload 무관, 고정 오버헤드), throughput ceiling ≈ **257K**(공유 DMA op-rate ÷ 4 DMA/RTT). 두 벽 모두 **구조적**.

### 슬라이드 P3-1 · `fig09_datapath.png` — 데이터 경로 (4-leg 체인)
- 4명의 actor: **HOST app**(descriptor post/consume), **DPU ARM**(단일 drain/route 스레드, body 안 읽음), **DPA EU**(forward-ring poll + `dma_copy ≤8KB` + completion), **DMA engine**(공유 HW, op-rate가 곧 천장).
- **왜 4-leg인가:** DPU가 `dst_pod_id`로 라우팅하려면 body를 자기 메모리에 **staging**해야 함 → host→host 직결 불가 → 반드시 host→DPU→host (= 4 dma_copy/RTT). 그리고 그 staging 버퍼를 reverse DMA가 **in-place**로 읽어 DPU staging copy는 0.

### 슬라이드 P3-2 · `fig10_rtt_breakdown.png` — 220µs는 어디로 가나
- 7-stage RTT attribution. dominant: **4 DMA poll-detect leg ~112µs** + **2 completion relay(DPA→ARM→host) ~60µs** + host stacks.
- payload sweep: 64B ≈ 8KB (+8µs뿐) → **고정 per-RTT 오버헤드, 전송시간 아님**. latency 줄이려면 transfer size가 아니라 hop 수/poll cadence/completion relay 공략.
- *정직하게:* TOTAL 220µs는 측정값, 7단계 분해는 4-lens **추정(Med confidence)**.

### 슬라이드 P3-3 · `fig11_latency_vs_load.png` — latency vs load
- p50가 30K~240K 내내 **flat ~220–340µs**, 240K까지 tail도 잘 통제(p99<1.3ms). 240K가 knee.
- (1K p50 371µs > 30K 222µs는 저부하<~4K에서 EU가 요청 사이에 park했다 wake하는 keepalive tax. ≥10K면 hot 유지.)

### 슬라이드 P3-4 · `fig12_cpu_scaling.png` — 어디가 먼저 포화되나
- **DPU ARM 단일 드레인 스레드가 39%→98%로 가장 먼저 포화**(busy-spin으로 completion reap). host client(≤51%)/echo(≤36%)는 여유.
- ⇒ 호스트가 throughput binder가 아님(멀티코어로 줘도 안 늘어남). ARM은 compute가 아니라 spin(-O2 중립).

### 슬라이드 P3-5 · `fig13_ceiling.png` — 천장은 구조적이다 (positive 증거)
- **8 EU/K4 = 4 EU/K2 = ~256K** — EU 2배도 0 이득(op-rate가 EU들 사이 공유). EU는 **~4까지만** 자원(1 EU=72K → 4 EU=257K, 3.5×).
- achieved가 target 올려도 **~257–258K로 plateau** = DMA op-rate(~1.03M ops/s) ÷ 4 DMA/RTT. 천장 너머는 M/M/1로 latency 폭발.
- host CPU 미포화 + ARM=spin → **CPU 벽이 아니라 공유 device 벽**.

### 슬라이드 P3-6 · `fig14_vs_tcp.png` — 왜 이게 중요한가 (baseline 대비)
- DPUmesh는 flat ~230µs p50, TCP+Envoy sidecar는 30K에서 **~40× 느림(9.3ms)**, 100K에서 **붕괴**(54ms, 15/1000만 성공 = Istio sidecar tax).
- 게다가 DPUmesh는 host core를 응용에 돌려줌(transport가 DPU에). *정직하게:* TCP 100K는 collapsed run.

**P3 발표자 talking points**
1. 현재는 진짜 L7이 아니라 **pod-id 라우터** — ARM은 `dst_pod_id`만 O(1) 조회, body 0바이트.
2. 4-DMA-leg인 이유 = host→host 직결이 불가능한 이유 = zero-copy가 성립하는 이유(staging 버퍼를 reverse가 in-place로 읽음).
3. **220µs는 전송시간이 아니라 고정 오버헤드**(64B≈8KB). 줄이려면 hop 수/cadence/relay 공략.
4. **천장 257K는 EU 부족이 아니라 공유 DMA op-rate 벽**(positive 증거 3종: 8EU=4EU, host 미포화, ARM=spin).
5. 한 DPU 안에서는 이미 구조적 벽(257K/220µs)에 도달 — 진짜 scale-out = **더 많은 DPU**, 진짜 ~2× = **host→host 재설계**(큰 프로젝트). 무비용 latency win 하나 = **load-adaptive REV_DONE flush**(~16µs/7%, throughput 비용 0).

## 예상 Q&A 대비
- **\"왜 8KB cap?\"** — DPA `dma_copy` 하드 한계. 더 큰 payload는 app 레이어 chunking(byte-stream 투명성은 Stage 2 과제).
- **\"왜 천장이 안 올라가나? 코어 더 주면?\"** — 측정상 8EU=4EU(공유 op-rate), host 미포화, ARM=spin. 한 DPU의 구조적 벽. 더 주려면 host→host(4→2 DMA, foreclosed) 재설계 또는 DPU 추가.
- **\"event-driven인데 왜 load 중엔 spin?\"** — EVENT_BLOCK 실험에서 4.5× 붕괴. dedicated core라 spin이 free, 재우면 ~5 syscalls/completion이 ~1µs 간격을 못 따라감.
- **\"진짜 L7 라우팅 되나?\"** — 현재는 pod-id 라우터(body 안 읽음). 진짜 L7은 host→host와 묶인 target architecture(미구현).
